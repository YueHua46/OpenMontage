# 沉淀方法，按方法卡批量出片

用途：一条片子验收通过后，把“怎么做出这种效果”和“怎么验收”沉淀成方法卡（playbook）。之后来了新产品或新需求，Agent 按方法卡重新写分镜和提示词，用同样的模型参数和验收规则批量生成，不用从 0 到 1 重新摸索。

方法卡保存的是做法，不是一段固定的提示词：镜头用途、拍法和节奏、产品结构约束、验收规则，以及已验证有效的写法示例。模型每次生成都有随机性，复用方法能减少试错，但不能保证每条一次到位，所以每个版本仍要走验收闭环。

下文 `<S>` 指 `<SKILL>/scripts`，命令都在仓库根目录用 `<PY>` 运行。

## 1. 每个项目都走验收闭环

生成用 `batch_generate.py`，验收用 `review_shots.py`。分辨率、比例和价格都从中转配置读，任何已配置的模型都能用（例如 Grok 720p）。

**审查员就是 Agent 自己。** 脚本只负责把画面放大到看得清（密集抽帧页、局部放大条、台词识别文字），并拒绝和记录自相矛盾的结论；它不做任何程序化的画面判断，也不改动生成画面。

### 1.0 带货、转化广告的默认结构

用户要“转化”“带货”“引导下单”的片子，又没给自己的结构时，按下面写，不要只罗列功能：

| 段落 | 约占时长 | 作用 | 例子（老人看护摄像头） |
|---|---|---|---|
| 钩子 | 0–3 秒 | 一个让目标人群停下来的具体场景或问题 | 老人滑倒，手机够不到 |
| 痛点 | 3–10 秒 | 放大“不买会怎样”，说清现有方案为什么不够 | 普通监控只能看，接不到求助 |
| 方案 | 10–18 秒 | 产品怎么解决这个痛点，突出最独特的一个功能 | 伸手按机身上的呼叫键，家人手机响起 |
| 证明 | 18–28 秒 | 其余卖点快速带过，作为加分项 | 云台、跟踪、夜视 |
| 下单引导 | 最后 3–5 秒 | 情绪落点 + 明确动作 | 家人安心通话；“Grab yours below ↓” |

痛点和方案必须是同一件事：钩子里的问题，正好由方案段的功能解决。提案时先给这张结构表，再给逐镜内容。

### 1.1 生成前：按类别推出每个镜头的验收规则

**先写对首帧。** 图生视频的首帧是这个镜头的起点，视频从它开始演。首帧画动作开始前一刻的状态，动作过程和结束状态写在视频提示词里。例如“老人滑倒”这一镜，首帧是她刚脚下打滑、重心开始偏出的一瞬（还没落地），视频提示词写“滑倒、扶住沙发、坐到地毯上并停住”；不要把首帧画成已经坐在地上的结果，否则视频里没有动作可演。下一镜的首帧要接上一镜的结束状态。姿态写成可见的物理事实（“臀部在地毯上，沙发坐垫空着”），不要写“坐得稳”“姿势协调”这类会把画面拉回正常坐姿的词。

不要只写用户举过的例子。对每个镜头，按下面 10 个类别逐一想清楚“这个镜头里什么必须成立”，从脚本、产品参考图和常识推出来：

| 类别 | 要想清楚的问题 | 例子 |
|---|---|---|
| `count` | 每种产品、零件、人物、道具各几个 | 恰好四台摄像头、四块板；不多出前景设备 |
| `structure` | 产品外形、部件连接与参考图一致 | 双天线、单镜头、PIR 不是第二颗镜头；板和摄像头是分体 |
| `motion` | 哪些部件能动、动多少；其余相对墙面不动 | 只有下半球水平转；太阳能板、上壳、天线不动 |
| `orientation` | 设备、屏幕、手朝哪；操作的是正确的一面 | 手机屏幕朝向操作者；点的是正面控件不是后盖 |
| `viewpoint` | 画中画（手机、监控画面）是谁、从哪看到的 | 监控画面是墙上摄像头的俯视视角，不会拍到摄像头自己 |
| `light` | 灯、LED、屏幕亮灭，白天还是夜晚 | 白天 LED 熄灭；夜视是四颗白光不是红光；手机屏幕亮着 |
| `text_ui` | 屏幕文字、App 界面、包装、产品印字 | 不出现乱码、水印、产品上多出的字 |
| `people` | 身份、服装一致；手、手指、肢体、表情自然 | 同一女主、同一件 T 恤；五根手指 |
| `action` | 脚本动作按顺序在镜头内完成 | 先点麦克风，再看家人，再看提醒 |
| `audio` | 台词、语种、声音（Agent 听不到，靠识别文字加用户试听） | 完整说出原句，无背景音乐 |

规则写进 spec：全片通用的放顶层 `checks`，单镜头的放镜头 `checks`，格式 `{"id": "...", "category": "motion", "text": "..."}`。确实不适用的类别写进镜头的 `na` 并说明原因，例如 `"na": {"viewpoint": "画面里没有屏幕"}`。要放大看的区域写进 `regions`（画面比例坐标 `[x, y, w, h]`），例如手机屏幕、产品、必须静止的部件、手。

`review_shots.py lint` 检查每个镜头每个类别都有规则或 `na` 理由，缺了不让往下走。

### 1.2 闭环步骤

1. `batch_generate.py --stage frames` 出首帧。
2. **首帧闸门：** `review_shots.py sheet --stage frames`，看它打印的审片图（`frame.jpg`，长边 1280 的 JPEG）和放大区域，按 1.3 的方法 `mark --stage frames`。不要打开原始 PNG（原因见 SKILL.md“看图”）。不通过的首帧用 `retake <镜头> --new-frame --frame-prompt-file 新首帧提示词.txt --reason "..."`，再 `batch_generate.py --stage frames --only <镜头...>`。首帧没判通过的镜头，`batch_generate.py --stage videos` 会跳过它。首帧一张约 ¥0.01，大部分问题（拿反手机、多出设备、灯亮着）在首帧就能拦下。跳过首帧审核（`--skip-frame-review`）需要用户同意。
3. `batch_generate.py --stage videos` 出视频。
4. `review_shots.py sheet [--lang es]`：每段按每秒 3 帧抽成大图页，每个 `regions` 区域在每一帧都裁出来放大成一条；装了 faster-whisper 时附上台词识别结果。
5. 按 1.3 审查并 `mark`。
6. 不通过的镜头：按 SKILL.md 的“默认修复路径”找原因（先看是不是首帧就错了），改提示词或首帧，再 `review_shots.py retake <镜头> --reason "偏差和改法" --prompt-file 新提示词.txt [--new-frame --frame-prompt-file 新首帧提示词.txt]`，然后 `batch_generate.py --only <镜头>`。新的一版存为 `<镜头>-take2.mp4`，旧版保留。几个镜头都要重做时，逐个 `retake` 后用一次 `--only a b c` 并发提交。不要自己命名文件、手动挪文件“转正”，选用哪一版由 `mark` 和 `status` 记录。
7. 次数用完脚本会拒绝重生成。此时把镜头标为“未通过/待人工验收”，说明偏差和已尝试的写法，由用户决定。
8. `review_shots.py status` 列出每个镜头的结论和已选用的版本（`sheet --take N` / `mark --take N` 可补审旧版本，例如给已经做完的项目补验收再沉淀方法卡），`edit.json` 的 `clip` 直接用这里的名字（如 `a2-take2`）。

### 1.3 审查方法（防止只看清单、防止自相矛盾）

1. **先看全，后对照。** 把每一页、每一条放大图都看完，先不回看提示词和规则，写下客观观察：各物体数量，什么动了、什么时候动的，设备和屏幕朝哪，屏幕里显示什么、从什么角度，手和手指，文字，灯。写进 `--observed`。
2. **再逐条回答规则。** 每条规则都要明确归入 `--ok` 或 `--failed`（`--ok rest` 表示其余全部成立）。没回答完不能下结论。
3. **清单外的问题照样不通过。** 看到任何物理上不可能、和参考图不一致、前后矛盾的地方，即使没有对应规则，也判不通过，并用 `--new-check 类别:描述` 补成新规则（`--new-check-global` 加到所有镜头）。新规则写回 spec，之后沉淀进方法卡。
4. **看不清就不判通过。** 静止画面分辨不了的（例如 LED 是亮着还是白色灯珠），把区域加进 `regions` 重新出图；仍看不清就写进观察，判不通过或请用户确认，不要默认没问题。
5. **结论要和记录一致。** 判通过不能带失败的规则；判不通过必须指出失败规则或新规则；台词识别相似度低于 0.9 却判通过，必须用 `--flag-note` 说明。脚本会拒绝矛盾的记录。

重生成和合成都受 SKILL.md“生成偏差的处理边界”约束：只能改输入后重新生成，不能修补生成画面。

## 2. 把验收过的项目沉淀成方法卡

1. `playbook.py save --project <id> --spec shots.json --name <方法名>`，生成 `playbooks/<方法名>.json` 草稿：
   - 通过的镜头：带上实际发送的提示词、首帧提示词和参考图，作为写法示例。
   - 没通过或没验收的镜头：标为 `unresolved` / `unreviewed`，只记失败原因作为教训，不当作示例。
   - 模型参数：取自通过的镜头实际用的工具和 spec 设置。
2. Agent 填写草稿里的 `TODO`：拍法和节奏、结构、产品规则、提示词的组织方式（例如“通用约束块 + 本镜动作 + 口播要求 + 禁止项”），以及未解决镜头的教训。依据是验收记录和用户的反馈，不要编造。
3. 把方法卡要点发给用户确认。用户同意后运行 `playbook.py check --playbook playbooks/<方法名>.json`，没有 TODO 且有验收规则才会标为 ready。

`playbooks/` 默认不提交到 git，里面有产品资料和本地路径。要给同事用时，由用户决定怎么分享。

## 3. 用方法卡做新的片子

用户说“按上次那条做”“用 P52 的做法”时，先运行 `playbook.py list` 列出本机已有的方法卡（名字、状态、来源项目、已验证的镜头），按来源项目和镜头用途找到对应的那张；找不到就问用户，不要凭记忆重写一套。

1. 读方法卡，先看 `method`（含 `model_notes`）和未解决镜头的教训，再按新需求（新产品、新场景、新人物、新台词）写新的 `shots.json`。每个镜头的 `purpose` 尽量沿用方法卡里的说法，提示词参考写法示例重新写，不要原样照抄旧产品的描述。
2. `playbook.py apply --playbook playbooks/<方法名>.json --project <新id> --spec shots.json`：补齐模型参数，挂上全局规则和对应镜头的规则，打印每个镜头的写法示例和教训。方法卡里没有的镜头会提示“新镜头类型”，要重点检查。
3. 照第 1 节的闭环生成和验收：`batch_generate.py --dry-run` 报价并经用户确认，出首帧，出视频，验收，有限次重生成。
4. 合成按 `references/compose.md`。

### 3.1 一次出多条：所有条目同步推进

用户要批量时，一开始就全部一起做，不先单做 1 条，生成全部并发。每条是独立项目，有自己的费用记录和验收记录；各条在同一个审核点一起停下，用户一次确认：

1. **提案：** 所有条目的镜头表、改了哪些场景/人物/台词、高风险镜头（方法卡里未解决的、新镜头类型）和报价汇成一张表（`batch_generate.py --project v1 v2 v3 --stage frames --dry-run` 一次报出每条和合计）。费用按条和按批次一起批准，例如“5 条，每条不超过 ¥10”。
2. **首帧：** `batch_generate.py --project v1 v2 v3 --stage frames`，所有条目的所有首帧一次并发提交。Agent 逐张审完后一起交给用户看。
3. **视频：** `batch_generate.py --project v1 v2 v3 --stage videos`，各条首帧通过的镜头一次并发提交；逐镜验收，不通过的改输入后同样一起重生成（`--only` 列出各条要重做的镜头）。
4. **试听：** 每条一个试听版，一起交给用户逐条确认，然后合成。

不传 `--spec` 时，每个项目读自己的 `projects/<id>/shots.json`（`plan_variants.py --create` 和 `playbook.py apply` 都可以写在这里）。所有条目的预算在提交前一起预留，任何一条超预算都不会提交任何任务。

同一个问题出现在多条里时（例如几条都长出双镜头），按共性问题处理：找出共同原因，统一改提示词或输入后再重生成，不要每条各试各的。

## 只换变量的简单裂变

故事、卖点和镜头完全不变，只换场景、人物或口播时，可以用变量模板：写 `master.json`，运行 `plan_variants.py --master master.json` 预览版本表、重复提醒和费用（价格从配置读），用户确认后加 `--create` 生成各版本项目。master 里可以写 `checks`、`max_retakes`、`video_inputs` 和 `playbook`，它们会带进每个版本的 spec。之后同样走第 1 节的验收闭环。

## 注意事项

- 多条片子用一次 `batch_generate.py --project ...` 一起跑，不要同时开多个进程。默认所有镜头一次并发提交；某个渠道返回 busy 时，在该模型配置里设 `limits.max_concurrent` 限流（见 `references/providers.md`）。
- 只有确实换了场景、人物和口播才算不同版本。不要声称能保证平台判定不重复，也不要把它当成规避平台检测的手段。
- 人物参考图要有使用权，不用真实名人或未授权的人物形象。
- Agent 听不到声音，每个版本的发音、音色和口型都需要用户抽查。台词比对只说明识别出的文字一致，不代表听感合格。
