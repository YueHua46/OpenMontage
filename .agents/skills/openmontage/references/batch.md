# 沉淀方法，按方法卡批量出片

用途：一条片子验收通过后，把“怎么做出这种效果”和“怎么验收”沉淀成方法卡（playbook）。之后来了新产品或新需求，Agent 按方法卡重新写分镜和提示词，用同样的模型参数和验收规则批量生成，不用从 0 到 1 重新摸索。

方法卡保存的是做法，不是一段固定的提示词：镜头用途、拍法和节奏、产品结构约束、验收规则，以及已验证有效的写法示例。模型每次生成都有随机性，复用方法能减少试错，但不能保证每条一次到位，所以每个版本仍要走验收闭环。

下文 `<S>` 指 `<SKILL>/scripts`，命令都在仓库根目录用 `<PY>` 运行。

## 1. 每个项目都走验收闭环

生成用 `batch_generate.py`，验收用 `review_shots.py`。分辨率、比例和价格都从中转配置读，任何已配置的模型都能用（例如 Grok 720p）。

**审查员就是 Agent 自己。** 脚本只负责把画面放大到看得清（密集抽帧页、局部放大条、台词识别文字），并拒绝和记录自相矛盾的结论；它不做任何程序化的画面判断，也不改动生成画面。

本节讲流程。真实项目里反复出现的具体失败（产品像 P 上去的、遮挡反了、摔倒演成坐下、东西悬在空中等）汇总在 `failure-modes.md`，写提示词和审片时都要对照；所选风格的观感要求在 `styles/`。

### 1.0 带货、转化广告的默认结构

用户要“转化”“带货”“引导下单”的片子，又没给自己的结构时，按下面写，不要只罗列功能（所选风格模板另有结构时以模板为准）：

| 段落 | 约占时长 | 作用 | 例子（老人看护摄像头） |
|---|---|---|---|
| 钩子 | 0–3 秒 | 一个让目标人群停下来的具体场景或问题 | 老人滑倒，手机够不到 |
| 痛点 | 3–10 秒 | 放大“不买会怎样”，说清现有方案为什么不够 | 普通监控只能看，接不到求助 |
| 方案 | 10–18 秒 | 产品怎么解决这个痛点，突出最独特的一个功能 | 伸手按机身上的呼叫键，家人手机响起 |
| 证明 | 18–28 秒 | 其余卖点快速带过，作为加分项 | 云台、跟踪、夜视 |
| 下单引导 | 最后 3–5 秒 | 情绪落点 + 明确动作 | 家人安心通话；“Grab yours below ↓” |

痛点和方案必须是同一件事：钩子里的问题，正好由方案段的功能解决。提案时先给这张结构表，再给逐镜内容。

### 1.05 生成前：逐镜判断模型能不能做，红色镜头改拍法

现在的视频模型有明确的能力边界：有些动作无论提示词写多细，都会出慢放、横着挪步、变形或换人。只靠“生成后发现、改提示词、再抽”，会抽到第 7 次还不真实（P52：$4，21 镜，逃跑、喊话、云台、穿越运镜仍不能用）。所以**写提示词之前，先给每个镜头分级**，记进 spec 的 `feasibility`：

| 级别 | 典型内容 | 做法 |
|---|---|---|
| 绿 | 固定或轻微手持；人站着或坐着说话、小手势；慢走、朝镜头走近；产品静置，只有环境在动 | 正常生成 |
| 黄 | 一个清楚的单一动作，1 秒内完成（按键、拿起手机、摔倒、关门）；跟着人慢走的手持镜头 | 按 1.16 写，首帧带势头，必要时用尾帧锁定；样片阶段先测 |
| 红 | 跑步、急转身、对画外声音做出反应再动作；多人互动走位；产品机械运动（云台转动、跟踪）；App/监控界面在动；镜头从一个物体穿到另一个构图、大幅推近或环绕；水流打在产品上 | **保留剧情和台词，改拍法**，见下 |

红色镜头的改法（按优先级）：

1. **用真实素材：** 产品机械动作、App 操作和监控画面，向用户要真机录像或手机录屏，原样使用（`compose.md`）。
2. **拆成切镜：** 一个复杂动作拆成两三个绿色镜头，靠剪辑完成。例如“听到喊声转身逃跑”拆成“他听到声音、脸转向一侧（近景，1 秒）”加“背影已经在跑、离开画面（2 秒，首帧就是跑动中的姿势）”。“镜头从产品穿到两人”拆成“产品近景”切“两人中景”。
3. **换成模型做得好的拍法：** 跑步用远景、背影、动作已经在进行中；反应用表情近景；运镜改成固定机位加切镜。
4. **换模型试这一镜**（需要用户同意），并把结果记进 `providers.md`。

改拍法不等于删剧情：剧情、台词、顺序和时长保留，只改“怎么拍”，并在提案里逐镜列出原拍法、新拍法和理由，由用户确认。**样片阶段先拿红色和黄色镜头试**，用户看过再批量。

### 1.1 生成前：按类别推出每个镜头的验收规则

**剧烈、突然的动作（摔倒、绊倒、碰撞、掉落）：** 首帧要带着动作的势头（已经失去平衡、正在前扑），而不是动作还没开始，或者引发动作的原因已经消失（例如拖鞋已经脱落在一边）。视频提示词的写法见 1.16。

**先写对首帧。** 图生视频的首帧是这个镜头的起点，视频从它开始演。首帧画动作开始前一刻的状态，动作过程和结束状态写在视频提示词里。例如“老人滑倒”这一镜，首帧是她刚脚下打滑、重心开始偏出的一瞬（还没落地），视频提示词写“滑倒、扶住沙发、坐到地毯上并停住”；不要把首帧画成已经坐在地上的结果，否则视频里没有动作可演。下一镜的首帧要接上一镜的结束状态。姿态写成可见的物理事实（“臀部在地毯上，沙发坐垫空着”），不要写“坐得稳”“姿势协调”这类会把画面拉回正常坐姿的词。

不要只写用户举过的例子。对每个镜头，按下面 12 个类别逐一想清楚“这个镜头里什么必须成立”，从脚本、产品参考图和常识推出来：

| 类别 | 要想清楚的问题 | 例子 |
|---|---|---|
| `count` | 每种产品、零件、人物、道具各几个 | 恰好四台摄像头、四块板；不多出前景设备 |
| `structure` | 产品外形、部件连接与参考图一致 | 双天线、单镜头、PIR 不是第二颗镜头；板和摄像头是分体 |
| `motion` | 哪些部件能动、动多少；其余相对墙面不动 | 只有下半球水平转；太阳能板、上壳、天线不动 |
| `orientation` | 设备、屏幕、手朝哪；操作的是正确的一面 | 手机屏幕朝向操作者；点的是正面控件不是后盖 |
| `viewpoint` | 画中画（手机、监控画面）是谁、从哪看到的 | 监控画面是墙上摄像头的俯视视角，不会拍到摄像头自己 |
| `light` | 灯、LED、屏幕亮灭，白天还是夜晚 | 白天 LED 熄灭；夜视是四颗白光不是红光；手机屏幕亮着 |
| `text_ui` | 屏幕文字、App 界面、包装、产品印字 | 不出现乱码、水印、产品上多出的字 |
| `people` | 身份、服装一致；手、手指、肢体、表情自然 | 同一女主、同一件 T 恤；五根手指 |
| `action` | 脚本动作按顺序在镜头内完成 | 先点麦克风，再看家人，再看提醒 |
| `audio` | 台词、语种、音轨；Agent先做ASR、异常片段复核与声学检查，可用音频理解工具时进一步分析。只有转写时不伪称听过；用户委托自主初审、声音意见后续反馈时，不重复要求试听确认 | 完整说出原句，无背景音乐；主观音色偏好与客观台词异常分别记录 |
| `continuity` | 跨镜头出现的人物、场景、道具是否一致；剧情依赖的位置和距离是否成立 | 同一人物的脸、年龄、发型、衣服和参考图一致；“够不到的手机”在每个镜头里都确实够不到 |
| `realism` | 画面观感是否符合所选风格模板（`references/styles/`）；有没有非预期的 AI 感 | UGC 实拍风：像手机随手拍；精致广告风：干净但皮肤、材质不塑料。都不应出现摆拍僵硬、塑料皮肤、渲染感产品 |

**遮挡关系（每个有人和产品同框的镜头都要查）：** 离镜头近的东西挡住远的东西。单独传入的产品参考图，常被模型当成贴纸盖在画面最上层，于是出现背景里的产品压在前景人物手臂上的情况。产品只是背景里的小物件时，不要单独传产品图，用已经包含产品的场景参考图；需要传时，在提示词里按“离镜头从近到远”列出层次，例如 `From nearest to farthest: her right forearm and hand; then the end table with the small white camera, partly hidden behind her forearm; then the sofa.` 这比只写 `behind` 更容易被遵守。最省事的是构图时就避开人和产品的半遮挡，除非剧情需要。**首帧里被完全挡住的东西，视频模型不知道它存在**：人一移开，模型会画出一张没有产品的桌子。之后会露出来、又需要出现的产品或道具，首帧里必须看得见（至少露出能认出的部分），或者用尾帧锁住；审首帧时要想到视频里人会往哪里动、会露出什么。审片时在人和产品重叠的地方加 `regions` 放大检查，这类问题记在 `realism` 或 `structure` 下。

单镜头、不和其他镜头共用人物或场景时，`continuity` 可以写进 `na`。有参考图时，在 `regions` 里加一条带参考的放大：`"face": {"box": [...], "ref": "@m-person", "ref_box": [...]}`，审片时参考图的同一部位会以 REF 标签排在最前面并排对比。

规则写进 spec：全片通用的放顶层 `checks`，单镜头的放镜头 `checks`，格式 `{"id": "...", "category": "motion", "text": "..."}`。确实不适用的类别写进镜头的 `na` 并说明原因，例如 `"na": {"viewpoint": "画面里没有屏幕"}`。要放大看的区域写进 `regions`（画面比例坐标 `[x, y, w, h]`），例如手机屏幕、产品、必须静止的部件、手。

`review_shots.py lint` 检查每个镜头每个类别都有规则或 `na` 理由，缺了不让往下走。

### 1.12 所有镜头的现实规律检查

本节是生成与验收的方法，不是把历史错误逐个写成禁止词。对本镜实际出现的物体和动作作以下推导，只把关键约束写进提示词；完整检查保留在spec和审查记录。

1. **物体和状态。** 列出实际存在的人、物、零件、服装与界面，以及起点和终点状态。没有进入、退出、遮挡或明确动作，数量、身份、拓扑结构、材质和尺度不能自行改变；刚体不能伸缩、换零件，裙子不能转身变成裤子。
2. **连接和自由度。** 明确什么固定在什么上、由谁支撑，哪些关节可动及范围。固定是相对于安装物而非画面像素；正常机位运动会让整体产生视差。软物可以随力变形，但端点和连接不能无故迁移，不能把所有软物都规定成刚体。
3. **原因、受力和时间。** 从真实起点推导动作：接触或驱动发生后才响应；落脚承重、抓握释放、重力、惯性、流体碰撞与流向合理，速度与动作量匹配。不能仅凭起止姿势正确认定中间自然；不靠删动作、减速或定格规避。
4. **空间和观察。** 检查同深度尺度、前后遮挡、可通过空间、碰撞与穿透；相机变化能解释投影变化，不能解释物体独立变大、跨越实物或瞬移。镜中、屏中和监控视角还要有正确来源。
5. **完整过程和边界。** 全镜至少6fps检查，快速接触、转身、遮挡后重现或状态突变处加密；同时看整体与覆盖全部连接的局部，并对照相邻切镜。写具体观察时点和因果依据，不用“符合物理学”一句替代证据。画面不可辨认时保留未验证，不假装做过物理仿真或实测。
6. **开放的失败判定。** 不在清单里的异常仍失败：先定位到物体持续性、连接/自由度、动力/时序、空间或观察来源等原因；补本镜规则，检查相同原因是否影响其他镜头，修实际输入后有限重生成。通用层保存检查方法，项目层保存尺寸与部件事实，案例库只用于说明，不能代替主动审查。

**运动先分清参照系。** 逐镜区分外部拍摄设备、被拍产品及安装物、屏幕里的光学视角、屏幕/UI四层；说明各层相对谁可动、因什么而动。手机轻晃不能授权监控视角沿路行走，手持风格不能授权固定产品独立晃动。安装式云台的镜头只绕实际轴转动，光心只允许由机械结构带来的小位移；巡视画面不能出现步行横移、上下起伏或穿行的近远景视差。用近处门柱/围栏和远处建筑的连续相对关系验证，不以“平顺”二字替代判断。没有云台指令的镜头，连可转动部件也应保持原姿态。画外声不是任何可见物体的运动原因。

**背景也有结构。** 车辆、家具、门窗等虽不是商品，也要有连贯的面、连接和遮挡；首帧检查不应只框人物。区分正常的释放把手、扶手/凹槽与重复部件，追踪它们如何连到同一个物体，而非只数近似形状。

### 1.15 跨镜头的人物和场景：先做参考图

只在同一个人物、场景或道具布局出现在多个镜头里时需要；每镜独立的片子（例如多个不同场景的混剪）跳过本节。

不要让每个镜头各自从文字生成同一个人或同一个场景，否则人会换脸、场景会变样。做法：

1. **参考图：** spec 里加 `"kind": "reference"` 的镜头（id 建议 `m-` 开头），只出图不出视频。需要几张由故事决定：每个反复出现的人物一张（正面半身，衣服发型就是片中的样子），每个反复出现的场景一张（从主要机位拍的全景，道具放在剧情需要的位置）。参考图先审（`sheet/mark --stage frames`），通过后交给用户确认，再出分镜。
2. **布局说明：** 剧情依赖位置或距离时（谁够得着什么、谁看得见什么），在 spec 顶层写 `"set_plan"`，用文字写清位置、距离和各镜头机位，提示词按它写，`continuity` 规则也按它写。
3. **分镜首帧** 的 `refs` 用 `"@<参考镜头 id>"` 引用参考图，`@id` 总是指向它当前的版本。生成顺序：先 `--only` 参考镜头，审完再生成其余镜头。

产品参考图只用干净的产品图（白底或实拍），不用带大段文字和图标的宣传图。

**身份母版不是衣服色卡。** 先比较现有四视图、原分镜及已生成参考是否互相矛盾，再选一套有效母版并记录来源和版本。脸部特征与完整体型都要可辨认：肩宽、颈部、胸腰腹、手臂与腿的粗细、衣服版型均保持。不要同时让旧分镜保留原体型、又让另一张参考提供新体型；编辑时明确旧图仅提供场景、机位和动作起点，角色外形统一由母版提供。近景不能只对脸，坐姿不能把肚腹鼓起一概解释为姿势，夜景也不能跳过轮廓检查。用等头部大小的脸部对照和保留完整躯干的体型对照一起审；只比较原始像素宽度无法排除透视。发现一套参考内部不一致时，暂停同类视频，先修正母版与受影响首帧。用户已明确委托自主选角和验收时按委托继续，不重复请求角色确认。

**整片设定表（多个镜头同一个故事时必做）：** 在 spec 顶层写 `"world"`，按场景锁定：地点（同一个院子、同一个客厅，各有参考图）、时间和天气（阴天就全段阴天，除非剧情写了时间推移）、光线方向、色调、每个人物的服装（要符合场景，例如泥泞牧场里不穿短裙露脐装，除非用户要求）。相邻镜头必须同一天气、同一时间、同一色调；手机界面镜头统一一种做法（都是手持拍屏幕，或都是录屏），不要混用。验收时把相邻镜头并排看，天气、光线、色调对不上就判 `continuity` 不通过。

### 1.155 带货产品的物理尺度

- 在项目spec记录尺寸来源、单位和量到哪里（机身/含天线/含支架），分别记录可核实数值与尚未知尺寸。没有依据不编造厘米值；同系列产品或生成图不能反向覆盖用户真机资料。
- 固定可复用的安装参考：产品、底座、太阳能板等部件比例，以及同一根柱子/桌面/手持物的关系。选择创作中的安装物尺寸时标明是场景设定，不冒充实测数据。
- 审查分清画幅占比与物理大小。推进/裁切会同时放大同深度的产品和安装物；用同安装高度附近的柱宽、安装板和接触点比较，不能拿前后不同深度的人头或整张图覆盖率直接下结论。透视或遮挡不足以判断时保留未验证状态，补清晰参考。
- 将产品结构、物理尺度、人物身份分别写成可回答的检查，先审全部相关首帧，再审视频首中尾与切镜两侧。只保持镜头/灯珠数量正确不代表尺寸正确；模型把摄像头变大、面板缩水或支架比例变了均失败。
- **安装位置和构图也要真实：** 户外安防摄像头一般装在 2.5–3 米高处（屋檐下、高杆顶），不在人头高度的矮木桩上；产品出镜用人和实物做尺度参照（手、门框、屋檐），不要把产品放在镜头最前面占半个画面，那样看起来比人还大。需要产品特写时单独拍近景，不和远处的人放进同一个透视里比大小。
- 用户提供的原分镜也要核对。明显失真的首帧在已有授权内重新生成完整参考画面，再生成视频；不能用局部缩放、贴片或后期改造产品像素掩盖。

### 1.16 视频提示词：让动作像真的

视频模型默认把动作做得慢、平、稳，并把提示词里的每一步平均摊满整段时长。真实动作有自己的速度：绊倒到落地不到一秒，按一下按钮半秒。写视频提示词时按下面检查：

1. **一段只演一个动作。** 不要把“绊一下、扔篮子、扶沙发、坐下、坐稳”五步写进 4 秒，模型会把每一步都演慢，看起来像故意的。
2. **片长按动作的真实时长定。** 动作本身多长，片长就接近多长，最多再加一两秒的“动作之后的状态”（愣住、喘气、静止）。摔倒类 2–3 秒，按键类 2–3 秒。
3. **写清动作在什么时候发生、多快。** 例如 `within the first second`、`sudden`、`real-time speed, not slow motion`。剩下的时间写成动作后的状态，不留空白给模型去发挥。
4. **用物理因果写，不用结果词。** 先写原因（脚尖被翘起的地毯边勾住），再写力（惯性把上身往前带、来不及迈步），最后写落点和姿势（重重落在手和胯上，落在边桌旁）。不写 `falls naturally` 这类只给结果的词。
5. **不用软化词。** `gently`、`slowly`、`sinks down`、`safely`、`carefully`、`no impact`、`not hurt` 会让模型做成受控的慢动作。安全方面只写最低限度（不出现血和伤口）。
6. **写身体反应，不写表演形容词。** 写“愣住、喘气、手撑着地”，不写 `dramatic`、`emotional`、`shocked expression`，后者会让人物开始演戏。
7. **用首尾帧锁住关键动作。** 起点要有动作的势头，终点固定结束姿势和位置（也解决和下一镜的衔接）。精细动作（按键、插线）的尾帧画出手指在正确部位上，并写“只碰 X，不碰 Y”。尾帧必须和首帧是同一机位、同一构图（用首帧做编辑、并排比对）；图像编辑保不住机位时不要用尾帧，否则视频会在中间硬把镜头扭过去。这种情况改为让首帧本身就站在动作会自然落到的位置。
8. **写清重力。** 被扔出、掉落的东西写 `falls to the floor at once`，否则模型可能让它在空中停一会儿。
9. **镜头运动越少越好。** 不需要时写 `fixed camera` 或 `slight handheld sway`。推近、环绕会让产品结构在运动中变形，产品镜头尤其要少动。
10. **只用模型做得像的运镜。** 能做：固定机位、轻微手持晃动、跟着人慢走的手持跟拍、很慢的小幅推近（不改变构图）。做不像：镜头从一个物体旁边穿过去到另一个构图（模型会把两张图“变形”过去，不是真的移动）、大幅推拉、环绕、升降。做不像的运镜改成两个镜头切过去。
11. **监控和云台视角另算。** 云台画面是绕一个固定点转：近处和远处一起平移、没有视差，地平线不倾斜，转动是匀速的一小段然后停住；不会像人拿着手机走路那样前进。模型很难做对，优先用真机录屏；要生成时只做固定不动的监控画面，转动用切镜表现，或者在后期做：**纯转动没有视差，所以在一段更宽的固定机位画面上平移裁切（匀速一小段后停住），物理上就是正确的云台转动；云台跟人时让裁切框跟着人物位置走**，人物位置用 opencv 追踪得到。人形检测框、通知横幅属于 App 界面层，在合成里画，不算修补生成画面。监控画面按真实摄像头出成 16:9（镜头里写 `"aspect_ratio": "16:9"`，首帧和视频都按它生成），合成时嵌进竖屏 App 界面；所有监控镜头从同一张监控视角参考图（`kind: reference`）出发，机位才一致。产品本身的云台转动、跟踪同理，优先用真机视频。
12. **画外声音引发的反应不要写进同一段。** “听到喊声 → 转头 → 逃跑”模型做不出合理的时机，会先慢慢走再横着挪。拆成反应近景和动作已经在进行中的镜头（见 1.05）。

审片时用 1.3 的方法，在动作时段按每秒 6 帧逐帧看，判断标准是按正常速度看像不像。

### 1.17 风格模板

画面观感（UGC 实拍感、精致广告感等）和对应的提示词写法放在 `references/styles/`，每种风格一个文件。提案时按用户的需求选模板，并写进 spec 顶层 `"style"`；`realism` 规则按模板写。没有合适的模板就按用户的描述写，片子验收通过后可以照 `references/styles/README.md` 新增一个。

### 1.2 闭环步骤

1. `batch_generate.py --stage frames` 出首帧。有参考图时先 `--only` 参考镜头，审过再出其余镜头（1.15）。
2. **首帧闸门：** `review_shots.py sheet --stage frames`，看它打印的审片图（`frame.jpg`，长边 1280 的 JPEG）和放大区域，按 1.3 的方法 `mark --stage frames`。不要打开原始 PNG（原因见 SKILL.md“看图”）。不通过的首帧用 `retake <镜头> --new-frame --frame-prompt-file 新首帧提示词.txt --reason "..."`，再 `batch_generate.py --stage frames --only <镜头...>`。首帧没判通过的镜头，`batch_generate.py --stage videos` 会跳过它。首帧一张约 ¥0.01，大部分问题（拿反手机、多出设备、灯亮着）在首帧就能拦下。跳过首帧审核（`--skip-frame-review`）需要用户同意。
3. `batch_generate.py --stage videos` 出视频。
4. `review_shots.py sheet [--lang es]`：每段默认按每秒 6 帧抽成大图页，每个 `regions` 区域在每一帧都裁出来放大成一条；装了 faster-whisper 时附上台词识别结果。快速状态变化处按1.12加密。
5. 按 1.3 审查并 `mark`。
6. 不通过的镜头：按 SKILL.md 的“默认修复路径”找原因（先看是不是首帧就错了），改提示词或首帧，再 `review_shots.py retake <镜头> --reason "偏差和改法" --prompt-file 新提示词.txt [--new-frame --frame-prompt-file 新首帧提示词.txt]`，然后 `batch_generate.py --only <镜头>`。新的一版存为 `<镜头>-take2.mp4`，旧版保留。几个镜头都要重做时，逐个 `retake` 后用一次 `--only a b c` 并发提交。不要自己命名文件、手动挪文件“转正”，选用哪一版由 `mark` 和 `status` 记录。
7. 次数用完脚本会拒绝重生成。此时把镜头标为“未通过/待人工验收”，说明偏差和已尝试的写法，由用户决定。
8. `review_shots.py status` 列出每个镜头的结论和已选用的版本（`sheet --take N` / `mark --take N` 可补审旧版本，例如给已经做完的项目补验收再沉淀方法卡），`edit.json` 的 `clip` 直接用这里的名字（如 `a2-take2`）。

### 1.3 审查方法（防止只看清单、防止自相矛盾）

**静态页不等于连续播放。** 有实际视频理解/播放感知能力时再按正常速度检查；只有图片工具时如实记录是连续抽帧推断，不能声称看过正常速度播放或全部源帧。对来回缩放、周期抖动、机位漂移，沿时间跟踪同一物体相对安装物和背景的位置/尺度；可使用只读轨迹诊断 motion_audit.py 定位可疑时段，数值不能自动证明物理正确。长条缩小看不清时用 sheet --region-pages product viewport 将指定区域分页，不能把“已生成证据”当成“已看清”。

**清晰度与交付成片再比较。** 分辨率、码率、解码和黑场检测通过只是技术条件。对相邻镜头的静止结构、商品和人物衣料以相同显示尺度比较细节；怀疑模糊时对照原片与输出同一时点，区分源片失焦、局部运动模糊和合成缩放/编码。不能用“监控本来略糊”解释所有质量突降。用户指出验收漏项时撤销受影响的通过结论，旧记录归档，更新最终报告，不能继续沿用旧的“仅声音待确认”。

1. **先看全，后对照。** 把每一页、每一条放大图都看完，先不回看提示词和规则，写下客观观察：各物体数量，什么动了、什么时候动的，设备和屏幕朝哪，屏幕里显示什么、从什么角度，手和手指，文字，灯。写进 `--observed`。
   **动作镜头先判断动作本身像不像。** 全镜抽帧不低于默认的每秒 6 帧；摔倒、绊倒、按键、接住或任何快速状态变化，在发生时段按需加密。要回答的是“观众按正常速度看一眼，能不能认出这是 X”，而不是“几张图的先后顺序对不对”：站着 → 弯腰 → 坐在地上，也可能只是慢慢坐下。描述时写出动作的力度和速度（失去平衡、突然、被惯性带倒，还是自己控制着放慢），对不上就判不通过。
   **用数字核算速度，不靠感觉。** 在逐帧页上量人物的身高（像素）和每秒移动的距离：正常走路每秒约 0.7–1 个身高，慢跑约 1.5–2 个，奔跑 2.5 个以上；步频走路约每秒 2 步，跑步约每秒 3 步。写“跑”的镜头低于每秒 1.5 个身高、或者每秒迈了好几步却几乎没前进（原地小碎步），就是慢放，判不通过。转身要看脚：先转头和上身、再蹬地转胯，是真实的；两条腿交叉横着挪、脚在地上滑，判不通过。（P52 S16：2 秒只移动约半个身高，转身时横向交叉挪步，不能用。）
2. **再逐条回答规则。** 每条规则都要明确归入 `--ok` 或 `--failed`（`--ok rest` 表示其余全部成立）。没回答完不能下结论。
3. **清单外的问题照样不通过。** 看到任何物理上不可能、和参考图不一致、前后矛盾的地方，即使没有对应规则，也判不通过，并用 `--new-check 类别:描述` 补成新规则（`--new-check-global` 加到所有镜头）。新规则写回 spec，之后沉淀进方法卡。
4. **看不清就不判通过。** 静止画面分辨不了的（例如 LED 是亮着还是白色灯珠），把区域加进 `regions` 重新出图；仍看不清就写进观察，判不通过或请用户确认，不要默认没问题。
5. **结论要和记录一致。** 判通过不能带失败的规则；判不通过必须指出失败规则或新规则；台词识别相似度低于 0.9 却判通过，必须用 `--flag-note` 说明。脚本会拒绝矛盾的记录。

重生成和合成都受 SKILL.md“生成偏差的处理边界”约束：只能改输入后重新生成，不能修补生成画面。

## 2. 把验收过的项目沉淀成方法卡

1. `playbook.py save --project <id> --spec shots.json --name <方法名>`，生成 `playbooks/<方法名>.json` 草稿：
   - 通过的镜头：带上实际发送的提示词、首帧提示词和参考图，作为写法示例。
   - 没通过或没验收的镜头：标为 `unresolved` / `unreviewed`，只记失败原因作为教训，不当作示例。
   - 模型参数：取自通过的镜头实际用的工具和 spec 设置。
2. Agent 填写草稿里的 `TODO`：拍法和节奏、结构、产品规则、提示词的组织方式（例如“通用约束块 + 本镜动作 + 口播要求 + 禁止项”），以及未解决镜头的教训。依据是验收记录和用户的反馈，不要编造。
3. 把方法卡要点发给用户确认。用户同意后运行 `playbook.py check --playbook playbooks/<方法名>.json`，没有 TODO 且有验收规则才会标为 ready。

`playbooks/` 默认不提交到 git，里面有产品资料和本地路径。要给同事用时，由用户决定怎么分享。

## 3. 用方法卡做新的片子

用户说“按上次那条做”“用 P52 的做法”时，先运行 `playbook.py list` 列出本机已有的方法卡（名字、状态、来源项目、已验证的镜头），按来源项目和镜头用途找到对应的那张；找不到就问用户，不要凭记忆重写一套。

1. 读方法卡，先看 `method`（含 `model_notes`）和未解决镜头的教训，再按新需求（新产品、新场景、新人物、新台词）写新的 `shots.json`。每个镜头的 `purpose` 尽量沿用方法卡里的说法，提示词参考写法示例重新写，不要原样照抄旧产品的描述。
2. `playbook.py apply --playbook playbooks/<方法名>.json --project <新id> --spec shots.json`：补齐模型参数，挂上全局规则和对应镜头的规则，打印每个镜头的写法示例和教训。方法卡里没有的镜头会提示“新镜头类型”，要重点检查。
3. 照第 1 节的闭环生成和验收：`batch_generate.py --dry-run` 报价并经用户确认，出首帧，出视频，验收，有限次重生成。
4. 合成按 `references/compose.md`。

### 3.1 一次出多条：所有条目同步推进

用户要批量时，一开始就全部一起做，不先单做 1 条，生成全部并发。每条是独立项目，有自己的费用记录和验收记录；各条在同一个审核点一起停下，用户一次确认：

1. **提案：** 所有条目的镜头表、改了哪些场景/人物/台词、高风险镜头（方法卡里未解决的、新镜头类型）和报价汇成一张表（`batch_generate.py --project v1 v2 v3 --stage frames --dry-run` 一次报出每条和合计）。费用按条和按批次一起批准，例如“5 条，每条不超过 ¥10”。
2. **首帧：** `batch_generate.py --project v1 v2 v3 --stage frames`，所有条目的所有首帧一次并发提交。Agent 逐张审完后一起交给用户看。
3. **视频：** `batch_generate.py --project v1 v2 v3 --stage videos`，各条首帧通过的镜头一次并发提交；逐镜验收，不通过的改输入后同样一起重生成（`--only` 列出各条要重做的镜头）。
4. **试听：** 每条一个试听版，默认一起交给用户逐条确认后合成；用户明确委托自主审片和合成时，按 `SKILL.md` 的确认例外执行，不扩大费用或重试授权。

不传 `--spec` 时，每个项目读自己的 `projects/<id>/shots.json`（`plan_variants.py --create` 和 `playbook.py apply` 都可以写在这里）。所有条目的预算在提交前一起预留，任何一条超预算都不会提交任何任务。

同一个问题出现在多条里时（例如几条都长出双镜头），按共性问题处理：找出共同原因，统一改提示词或输入后再重生成，不要每条各试各的。

## 只换变量的简单裂变

故事、卖点和镜头完全不变，只换场景、人物或口播时，可以用变量模板：写 `master.json`，运行 `plan_variants.py --master master.json` 预览版本表、重复提醒和费用（价格从配置读），用户确认后加 `--create` 生成各版本项目。master 里可以写 `checks`、`max_retakes`、`video_inputs` 和 `playbook`，它们会带进每个版本的 spec。之后同样走第 1 节的验收闭环。

## 注意事项

- 多条片子用一次 `batch_generate.py --project ...` 一起跑，不要同时开多个进程。默认所有镜头一次并发提交；某个渠道返回 busy 时，在该模型配置里设 `limits.max_concurrent` 限流（见 `references/providers.md`）。
- 只有确实换了场景、人物和口播才算不同版本。不要声称能保证平台判定不重复，也不要把它当成规避平台检测的手段。
- 人物参考图要有使用权，不用真实名人或未授权的人物形象。
- Agent 听不到声音，每个版本的发音、音色和口型都需要用户抽查。台词比对只说明识别出的文字一致，不代表听感合格。
