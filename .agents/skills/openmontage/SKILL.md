# OpenMontage 成片

下文 `<SKILL>` 指本 `SKILL.md` 所在目录，`<PY>` 指仓库虚拟环境的 Python：Windows 为 `.venv/Scripts/python.exe -X utf8`，macOS/Linux 为 `.venv/bin/python -X utf8`。不要使用系统默认 Python。

本技能随 OpenMontage 仓库分发，位于仓库 `.agents/skills/openmontage`。用户级入口 `~/.agents/skills/openmontage`（Codex）和 `~/.claude/skills/openmontage`（Claude Code）都是指向这个目录的链接，不是副本：要改技能只改仓库里的，不要在用户目录另放一份。经链接打开本文件时，不能从链接位置往上推算仓库；以 `doctor.py` 第一行 `OpenMontage repo:` 打印的路径为仓库根目录（它会解析链接，也认 `OPENMONTAGE_HOME`）。所有命令在仓库目录下执行；用户素材用绝对路径引用，先确认文件存在。

本技能的脚本（`batch_generate.py`、`review_shots.py`、`qc_media.py`、`preview.py`、`playbook.py`、`app_feed.py` 等）都在 `.agents/skills/openmontage/scripts/`。仓库根目录的 `scripts/` 是另一组无关脚本，在那里找不到它们不代表脚本不存在。

## 开工前

1. 运行 `python <SKILL>/scripts/doctor.py`。缺 Python 包（Pillow、numpy、faster-whisper 等）或 ffmpeg、Node.js、git 时，直接运行 `doctor.py --fix` 安装，装完再检查，环境要齐全，不要因为缺依赖就跳过审片或切分步骤。只有缺密钥时才停下：让用户自己写入仓库 `.env`，不要让用户把密钥发到对话里，绝不打印密钥值。在 Codex 沙箱里装不上时，申请在沙箱外运行。
2. 读仓库 `AGENT_GUIDE.md`（强制），再读 `.agents/skills/relay-providers/SKILL.md`、`skills/core/relay-providers.md`，以及本技能 `references/providers.md`。写提示词前读 `references/failure-modes.md` 和所选风格模板（`references/styles/`），合成前读 `references/compose.md`。
3. 运行 `<PY> -m tools.relay route` 确认默认渠道。接入或切换渠道按 `references/providers.md` 处理，不启动成片流水线或付费测试。

## 更新

用户说“更新 OpenMontage”时，在仓库根目录运行 `update.cmd --no-pause`。它拉取 `main`、安装依赖并运行 `doctor.py`，技能、代码和渠道配置一起更新，密钥不受影响。

- 拉取失败时把报错原样告诉用户。本地有改动时不要丢弃，也不要强制覆盖。
- Codex 沙箱不允许写 `.git` 时，申请在沙箱外运行；申请不了时，让用户双击仓库里的 `update.cmd`。
- 更新后告诉用户重启 Agent，让新版技能生效。

## 在 Codex 中运行

本技能同时用于 Claude Code 和 Codex。在 Codex 中还要注意：

- 用仓库里的 `codex-video.cmd` 启动。它进入仓库目录，在 `workspace-write` 沙箱内打开联网，并隐藏沙箱里启动不了的 Store 版 `pwsh`。`doctor.py` 报网络不通时，让用户退出后用它重新启动。
- Windows 沙箱里渲染器启动不了（`EPERM`）。合成到渲染时，申请在沙箱外运行 `scripts/render.py`，由用户批准；申请不了时，把完整命令交给用户在自己的终端运行。其他步骤都留在沙箱内。
- 视频生成和渲染可能超过单条命令的时限：`pending` 时用相同参数再次调用来恢复，不要重新提交。
- 没有向用户发送文件的工具时，报告文件的完整路径，让用户自己打开试听。

## 成片流程

走 `cinematic` 流水线（Rule Zero），用 `lib.checkpoint` 写检查点，遵守审批闸门。

1. **看素材：** 读完用户给的全部脚本、图片和参考视频（抽帧、测时长和切点）。图片和视频帧先用 `scripts/preview.py` 转成小图再看（见下文“看图”）。只有模糊要求时按 `skills/meta/creative-intake.md` 的 “Handling Open, Media-Led Briefs” 自己推断，最多问一个阻塞问题。
2. **提案：** 一次列清镜头表、费用、分辨率、配音方案和需要用户决定的默认项。用户已给完整脚本或分镜时，脚本和分镜随提案一起批准，不再逐阶段确认。带货、转化广告默认按 `references/batch.md` 1.0 的“钩子 → 痛点 → 方案 → 证明 → 下单引导”结构写，用户另有结构时按用户的。按用户要的观感从 `references/styles/` 选风格模板（例如 TK 引流、要像真人实拍时用 `tiktok-ugc.md`），在提案里说明选了哪个；没有合适的模板就按用户描述写，不硬套。
3. **样片：** 第一次付费前展示 `dry_run`。没有方法卡、又有人物对白或新的语言时，先生成 2–3 段样片，由 Agent 完成逐帧审查、ASR 台词核对及可用的音轨检查，再交用户预览。默认确认后再批量；用户已明确委托 Agent 自主初审、声音意见后续再反馈时，按该委托继续已授权范围内的制作，不重复要求用户承担常规审片或把音色偏好确认作为停工条件。该委托不扩大付费预算、重试次数或模型/渠道授权。按已就绪的方法卡批量时不单做样片，所有条目同步推进（`references/batch.md` 3.1）。
4. **批量生成：** 把镜头写成 spec，用 `scripts/batch_generate.py`：先生成首帧并逐张检查，再生成视频（`--dry-run` 可预览）。它已处理费用记录、并发提交和跳过已有文件；多条片子用 `--project v1 v2 v3` 一次并发跑完。
5. **检查：** 用 `scripts/qc_media.py <目录> --sheets <目录>` 测尺寸、解码、切镜和有声区间，再看抽帧表；用 ASR 核对台词，异常片段先自行分段复核。偏差如实报告，在已有授权和预算内处理，不把 Agent 可完成的检查交还用户。
6. **素材确认：** 把原片首尾相接的试听版交给用户；默认确认后才合成。用户已明确委托 Agent 自主审片并合成时，完成客观检查、保留异常记录后按委托推进，不因用户尚未试听音色而停工；无授权的付费生成仍不能执行。
7. **合成：** 按 `references/compose.md` 用 `scripts/assemble.py` 和 `hyperframes_compose`，成片放 `projects/<id>/renders/final.mp4`，保留原片。
8. **验收：** 对成片再跑 `qc_media.py` 并抽帧，写 `render_report`、`final_review` 和 compose 检查点。发布阶段只在用户要求时执行。

第 2 步的创意和费用授权必须落实；第 3、6 步默认等待用户确认，但用户已明确委托 Agent 自主验收或表示声音问题以后反馈时，以该委托为准，不重复索取同一确认。保留原片和真实审查结论，不能用委托掩盖缺陷或扩大预算。首帧有明显问题时先报告，在已有授权内修正后再生成对应视频。

第 4、5 步按 `references/batch.md` 第 1 节走验收闭环，审查员是你自己：同一人物或场景出现在多个镜头时，先出参考图（`"kind": "reference"`）并经用户确认，分镜用 `@id` 引用它（`references/batch.md` 1.15）；生成前按 12 个类别（含跨镜连贯 `continuity` 和符合风格模板的观感 `realism`）推出每个镜头的验收规则（不只是用户举的例子），首帧先审再出视频；用 `scripts/review_shots.py` 出放大的抽帧页，先写客观观察再逐条对照，清单外的问题同样判不通过并补成新规则；不通过的镜头改输入后有限次重生成，旧版保留。首帧是镜头动作的起点，不是动作的结果（`references/batch.md` 1.1）；视频提示词按 1.16 写，让动作按真实速度发生。

**写提示词之前，先按 `references/batch.md` 1.05 给每个镜头分级（绿/黄/红）。** 红色镜头（跑步、听到声音后反应、多人走位、产品机械运动、界面在动、穿越运镜等）保留剧情和台词、改成模型做得像的拍法或用真实素材，提案里逐镜说明并由用户确认；样片阶段先测红黄镜头。不要把模型做不好的动作直接交给它反复抽。

**写首帧和视频提示词之前，读 `references/failure-modes.md`；审每张首帧、每段视频时按它逐条对照。** 里面是真实项目里被用户一眼看穿的问题：产品像 P 上去的、遮挡反了、被挡住的产品在视频里消失、人物换脸、摔倒演成坐下、东西悬在空中、按错部位、运镜让产品变形、字幕挡住产品等，每条都写了原因、预防和发现方法。**用户指出的每个问题、你自己发现的每个新问题，当轮就补进 `failure-modes.md`（只属于某种风格的补进对应模板），写清原因和预防方法，并告诉用户补在哪里；不要等用户提醒。** 能用脚本检查的就补进脚本（例如 `voice_check.py`、`review_shots.py` 的规则），不能只靠文字。动作镜头必须按每秒 6 帧逐帧看动作时段，判断标准是“观众按正常速度看一眼像不像”，而不是几张图的先后顺序对不对。

**付费生成只走 `batch_generate.py`，重生成只走 `review_shots.py retake` + `batch_generate.py --only`。** 不要用 `registry.get(...).execute()`、`python -c` 或自写脚本直接调生成工具：那样不进 `cost_log.json`，绕开预算、重生成次数和首帧闸门，版本命名也和 `review.json` 对不上。直接调工具只用于 `dry_run` 查看请求。预算或次数不够时，先问用户，再改 spec 的 `budget_usd` / `max_retakes`。用户授权“有问题自己重做”，同样走这条路径。多个镜头要重做时一起 `retake`，再用一次 `--only a b c` 并发提交，不要一张一张串行跑。

### 原稿与身份输入检查

运动验收按 references/batch.md 1.12、1.3 分清外部机位、产品安装关系、屏内视角与UI；跟踪整个过程的相对位置和尺度，检查背景结构及相邻镜头清晰度。6fps抽帧不是连续播放或全部源帧，不能把生成审片页当成已完成运动判断。相同首尾帧不能作为外观锁定器；确需使用时记录依据，批处理会拦截无说明的相同尾帧。

- **物理与常识检查适用于所有物体和动作，不以已知故障清单为边界。** 生成前按 `references/batch.md` 1.12 建立本镜的物体、连接、支撑、可动范围和起止状态；审查时先独立观察完整过程，再检查结构与尺度是否持续、运动是否有原因、接触与遮挡是否成立。首尾正确不能抵消中间违反常理。新异常先判失败、归入通用原因，再记录具体案例；不能只给卷线、水流等已出过问题的对象加禁令，也不能要求用户逐个发现。

- 用户要求优化生成缺陷时，先锁定原稿镜数、顺序、台词、关键动作和总时长；风格模板不能覆盖这些要求。逐镜对照后才交付，不能删剧情或缩短片子来规避生成难点。
- 对照已确认人物参考，先审用户分镜首帧本身的脸、年龄、胡须、领口、发型和服装。原始分镜也可能有漂移；不能因为文件来自用户就当作身份已一致。
- 重复角色只设一套有效母版，先排除参考图之间的矛盾；同时固定脸型与体型（肩宽、颈围、胸腰、四肢粗细和衣服松紧），不能只因帽子、衣服相同就通过。用母版与所有出镜首帧并排比对脸部和完整躯干，坐姿、近景、夜景也要核对；姿势、透视和衣褶可以变化，人物不能忽胖忽瘦。用户已委托自主定角色和审片时，Agent选定并记录母版后继续，不重复要求用户选人。细则见 `references/batch.md` 1.15。
- 带货镜头另做产品物理尺度检查：从真实尺寸图锁定单位、测量范围和部件比例，以同深度的安装物/手持参照核对所有首帧、视频过程及切镜处。镜头远近可以改变画面占比，不能改变产品与同一安装物的相对大小；原始分镜同样可能错误。通用方法见 `references/batch.md` 1.155，具体尺寸只写项目spec，不写成通用产品常量。
- 记录**实际发送**的首帧、尾帧、独立参考图及工具支持的输入模式。Agent看过四视图、提示词写“同一个人”、spec列了未发送的参考路径，都不等于模型收到身份参考。缺少多图参考能力时如实说明，不传未声明字段。
- 从虚焦小人物推进到清晰近景时，检查身份能否从输入辨认；需要首尾帧时，尾帧必须是同一人物、服装、场景和合理终点，保留原定连续运镜。不能把开场复制为尾帧来取消原动作，也不能把另一模型结果偷偷当原始对照输入。
- 无人环境、产品特写和App镜头使用各自的局部提示词；画外声明确写为off-screen且镜内无人，不套用男女主出镜模板。审片同时核对人物数量、原台词和持续动作，不能只检查产品外形。
- 发现系统性换脸、陌生人入镜或关键动作丢失时，暂停同类付费批量，记录根因并修改有效输入后再解除hold；不能只添加“保持一致”就宣布已解决。具体案例见 `references/failure-modes.md` 的P52记录。

## 看图

Codex、Claude Code 会把你看过的每张图以 base64 留在对话历史里，之后每次请求都整段重发。原始 PNG 一张 2–3 MB，几十张就会让请求体超过中转网关上限，报 `413 Payload Too Large` / `Request Entity Too Large`，对话直接中断，这时 token 往往才用了两成。模型看图时本来就会缩到约 1280–2048 像素，大文件只增加字节，不增加细节。

- 只看脚本产出的 JPEG：首帧和视频用 `review_shots.py sheet` 打印的 `frame`、`page`、`zoom` 文件；其他图片（用户素材、产品参考图、临时看一眼的视频帧）先运行 `<PY> <SKILL>/scripts/preview.py <文件或目录> [--times 0.5 2]`，再看它打印的路径。
- 不直接打开 `assets/images/*.png`、`assets/video/*.mp4` 或自己用 ffmpeg 抽出的 PNG；不用 `detail: "original"`。
- 看不清细节就在 spec 的 `regions` 里加放大区域，重新 `sheet --only <镜头>`，不要换成看原图。
- 同一张图不重复看；一次调用里看的图控制在 6 张以内。
- 已经出现 413 时，这个对话之后的每次请求都会带着同样的历史，基本都会被拒（`/compact` 多半也要上传整段历史）。告诉用户新开一个对话，从项目检查点和 `review_shots.py status` 接着做。

## 对话压缩或交接之后

长任务中途对话被压缩，或者换到新对话时，先恢复状态，不要凭摘要重新摸索：

1. 写交接摘要时必须包括：项目 id、spec 路径、本技能脚本目录 `.agents/skills/openmontage/scripts/`、各镜头当前 take 和审核结论、已用费用和剩余预算、用户的最新授权范围和创意修正。
2. 接手后重新读本文件，然后运行 `review_shots.py status --project <id> --spec projects/<id>/shots.json`，并读 `projects/<id>/cost_log.json`，按里面的状态接着走第 1 节的闭环。
3. 摘要里说的“已通过”“已花费”要以这两个文件为准；对不上时告诉用户。

一条片子验收通过后，用户想复用这套做法，或者要求批量出类似的片子时，按 `references/batch.md` 用 `scripts/playbook.py` 把项目沉淀成方法卡，再按方法卡写新需求的分镜（用户提到“上次那条”时先 `playbook.py list` 找已有的方法卡），每个审核点都要停下。只换场景、人物或台词的简单裂变，可以用同一文件里的变量模板。

## 硬规则

- 生成时用 `preferred_tool` 锁定已批准的工具。`pending` 用相同参数再调用即可恢复，绝不重新提交；未经批准不换供应商或模型。
- 付费重试需要用户批准，并传 `confirm_resubmit: true`（脚本的 `--resubmit`）。
- 汇报费用时区分配置估算与可核实的实际扣费，超过批准预算前必须先问。
- 密钥只放在仓库 `.env` 或环境变量，不写入技能、YAML、示例、日志或交付物。
- Agent 负责先完成可用的音频与画面检查：用 Whisper/ASR 核对台词和时间，用 `qc_media.py` 检查响度、峰值和有声区间；异常转写先分段复核，口型结合相应画面检查。若有真正的音频理解工具，可用它进一步判断；只有 ASR 与声学指标时，要说明证据边界，不能声称亲耳听过、不能把音高接近或转写一致当成音色自然/同一说话人的证明。用户明确允许声音意见后续反馈时，不把未试听当成失败项或停工门槛；只保留具体尚不能验证的风险。
- 演示产品功能的 AI 画面不是实拍：默认不在画面上加 “simulated”“Dramatization” 类标注小字，提醒用户发布时打开平台的 AI 内容标签；用户要求时才加到画面里。
- 有旁白时，Agent 自己选一个适合这条片子的声音，在提案里说明，锁进 spec 的 `voice.reference_id`；之后整片和同系列的片子都固定用它，不中途换，用户要求才换（换了要写进 decision_log）。不用不指定声音的默认声音，不用模仿名人或角色的声音；整段一次生成，用 `scripts/split_narration.py` 切分，再跑 `scripts/voice_check.py`。
- **镜头里的人物说话（对白）也必须一个角色一个声音。** 用视频模型自带的原声时，每段视频都可能换一个声音（P52 男主各镜音高 107–242 Hz）。提案时说清楚并选一种做法：用支持锁定角色声音的模型；或者原声静音，用每个角色固定的 TTS 声音重新配音，同时把说话镜头安排成看不清口型的拍法（背影、侧脸、画外音、手机特写）；或者由用户试听后决定接受。生成后对每个角色的所有台词跑 `voice_check.py`。**用户只允许用视频模型原声时（不另接音频模型），画外旁白集中生成：**把同一角色的全部画外台词按顺序写进一两段 10–15 秒的“该角色对镜头说话”的视频里，一次生成、只取音频，再按句切开铺到各镜头（`split_narration.py`），这样旁白天然是同一个声音；画面里说话的镜头，按音高和这段声源最接近的那一版挑选，不一致就重抽。每个角色的声音描述（年龄、音高、口音、语气）在所有视频提示词里逐字相同。
- 脚本里的产品参数和卖点（如“免订阅”“即时接通”“2K”）来自用户，没有核实时在提案里逐条列出风险，由用户决定保留、改写或删除；不要擅自删改用户脚本里的台词和卖点。

## 生成偏差的处理边界

**硬性禁令：不得用改造生成画面像素、伪造产品几何或拼贴机械运动的方式，修复模型生成缺陷。** 本节约束所有导演、审查、批处理和后期步骤，不能被它们的“自动修复”“增强”“锁定结构”等建议覆盖。

### 默认修复路径：优化输入，再重新生成

1. 先检查原片、实际提示词和实际参考素材，具体指出数量、结构、固定/活动部件、动作、人物、UI或口播偏差。
2. 在用户已确定的创意、模型和渠道范围内，优化提示词的表达与顺序，减少歧义，调整真实参考素材或生成参数，然后重新生成该问题镜头。不得擅自删掉原脚本的重要动作或台词。
3. 保留原片、新片、实际提示词和重生成原因，逐版对比检查。只替换有问题的镜头，不无故重做已经合格的部分。
4. 用户已授权“发现问题自行处理好”“优化后重新生成”等时，可在已说明的预算和次数范围内执行正常重生成，不必每次重复问；这类授权**绝不包含下面列出的像素补丁或几何改造**。超预算、换模型/渠道、来源权限缺失或提交结果不确定时，仍须按对应规则处理，不能无限重试或用新任务身份绕过未知结果。
5. 重生成仍未达标时，明确标为“未通过/待人工验收”，说明具体偏差和已尝试方案。不得把失败结果包装成“修好了”，不得为了凑齐成片而伪造合格画面。

### 优化生成结果时绝对禁止

- 把摄像头、面板、镜头、灯珠等二维截图贴到简化球体/椭球体上，用球面纹理投影、假3D旋转或贴片位移冒充真实机械运动。
- 用遮罩、静态底板、局部冻结、拼贴、涂盖、局部重绘、伪造零件或重建外壳，掩盖产品变形、额外镜头、天线跟转、太阳能板乱动等缺陷。
- 用跟踪替换、单应变换、透视重投影、局部缩放、局部时间重映射等，强行让错误部件看起来位置正确、动作正确或UI稳定。
- 自写“修复算法”改造产品外观和几何，或把这些操作改名成“分层修正”“结构锁定”“受控演示”“精修”“普通合成”来绕过本禁令。
- 把先前另一模型的成片、抽帧或已生成结果，偷偷作为独立模型对照测试的输入。对照测试必须使用用户指定的原始素材与脚本；需要改变测试条件时先说明。

用户说“保持UI固定”“只有下半球转动”“把问题处理好”，是质量目标，不是让Agent下载后用代码伪造该目标的授权。不得因人工补片在几张抽帧里看似对齐，就声称真实、自然、无撕裂或验收通过。

### 正常剪辑与原素材处理的范围

用户要求的硬切、拼接、裁剪时长、静音、响度调整及保持比例的全画面输出缩放，可以按已约定范围执行；它们不得夹带产品局部变形或画面修补。单独授权的原素材去角标，只能处理该原素材的指定角标，不能扩大成修改模型视频、产品结构或UI控件的授权。

本禁令针对“修复生成缺陷”，不把用户另行明确委托的独立三维动画或特效创作混为一谈；不得把生成修复改称独立特效任务来规避本禁令。

需要旁白时根据本次 preflight 确认 TTS 能力；不可用时说明缺口，不擅自替换供应商或删掉用户要求的旁白。
